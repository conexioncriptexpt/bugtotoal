## Evidence (verbatim)
- trigger_indie: `deployer indie returned status 409: {"code":"deployment_blocked","error":"This deployment was blocked. If you believe this is a mistake, please contact support."}` (type: deployer_indie_4xx, retryable: false)

## Root Cause
The deployment was rejected by the platform's abuse/phishing classification gate (`await_phishing` / `AwaitPhishingClassification`), which returned 409 `deployment_blocked`. This is a platform-side policy block that fires before build/source steps. No build, secret, tier, manifest, or source condition is involved — none of those were reached.

## Why no fix was applied
- The block is non-retryable at the trigger (`retryable: false`). Re-firing resume_pipeline will return the same 409.
- There is no deployer-agent tool that can clear an anti-phishing/abuse block. It must be reviewed and lifted by Emergent support.

## Recommended action
1. If the user believes this is a false positive, contact Emergent Support quoting deployment_id 7b10ae89-d5e8-43c6-a2d5-9a56b1b45faf and job_id 9161239e-a9d5-4804-af8c-f687a0a918db to have the block reviewed/lifted.
2. The platform message also suggests forking the session and starting a new deployment.
