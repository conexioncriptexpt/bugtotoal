# RCA — conex-assist-1 `/api/me` 500 ("Acesso não autorizado") in production

## Symptom
Signing in on production (https://conex-assist-1.emergent.host) as `garciafinancas0073040@proton.me`, then opening `/crm`, shows "Acesso não autorizado — Não foi possível carregar a sua conta". Works in preview.

## What `/api/me` actually returns
**HTTP 500**, not 401/403. The Clerk JWT verifies fine (no 401) and the request reaches member resolution. Stack trace from prod logs (active run `da0c9d88`):

```
GET /api/me HTTP/1.1" 500 Internal Server Error
...
File "/app/backend/core.py", line 109, in current_member
    return await resolve_member(user["user_id"])
File "/app/backend/core.py", line 96, in resolve_member
    await db.users.insert_one(...)
pymongo.errors.DuplicateKeyError: E11000 duplicate key error collection:
  conex-assist-1-test_database.users index: email_1 dup key:
  { email: "garciafinancas0073040@proton.me" }
```

## Root cause (two layers, both proven)

### 1. Clerk instance mismatch: preview = test, production = live
- Committed source `backend/.env` uses **pk_test / sk_test** (`pk_test_cmV...`, test/dev Clerk instance).
- Production `CLERK_PUBLISHABLE_KEY` and `CLERK_SECRET_KEY` do **NOT** equal those committed test values (`list_secrets` `matches_expected=false` for both), and `clerk_auth.py` only relays through the `/api/__clerk` proxy when the key `startswith("pk_live_")`. Prod logs show `/api/__clerk/...` serving 200s → **production runs a pk_live/sk_live (LIVE) Clerk instance.** (This is the correct/intended setup for prod — the secrets are not "wrong".)
- Consequence: the user's Clerk **user_id in the LIVE instance differs** from the user_id stored in the migrated DB doc, which was created under the TEST instance.

### 2. `resolve_member` cannot reconcile a migrated doc with a stale user_id → unhandled 500
`db.users` has exactly ONE doc for this email:
```
email:   garciafinancas0073040@proton.me
user_id: user_3LPinI6yAtcdMmuJrAKDz5xQjYS   <-- TEST-instance uid, migrated from preview
env:     preview
role:    super_admin, active: true
id:      21f43c32-b1d6-465f-a4e4-005ec27ed906
```
Indexes: `email_1` is **unique**; `user_id_1` is non-unique.

`resolve_member(uid)` flow for the LIVE uid:
1. `find_one({"user_id": <live uid>})` → **miss** (stored doc holds the old test uid).
2. Link-existing branch matches only `{"email": {"$in": verified}, "user_id": None}` → **miss** (the stored doc's `user_id` is a non-null stale value, not `None`).
3. Email is in `ADMIN_EMAIL` → falls to the auto-create branch: `insert_one({... email: ...})` → collides with the unique `email_1` index → **DuplicateKeyError → HTTP 500.**

Why preview works: preview uses the same TEST instance that minted the stored user_id, so step 1 hits and returns immediately — the insert path is never reached.

## Fixes

### A. Code (E1) — robust fix
In `backend/core.py` `resolve_member`, reconcile by email even when the existing doc has a stale/non-null `user_id`:
- Broaden the link lookup from `{"email": {"$in": verified}, "user_id": None}` to match the existing email doc regardless of its current `user_id` (e.g. `{"email": {"$in": verified}}`), and **update** that doc's `user_id` to the new uid instead of inserting; and/or
- Wrap the `insert_one` in `try/except DuplicateKeyError` that falls back to re-linking the existing email doc's `user_id`.
This resolves the 500 for this account and any other migrated/test→live account.

### B. User (DB Manager) — immediate unblock, no redeploy
Edit the single `users` doc (id `21f43c32-b1d6-465f-a4e4-005ec27ed906`, email `garciafinancas0073040@proton.me`):
- Safest: set its `user_id` to `null` — the existing link-by-email branch (`user_id: None`) will then adopt the live uid on next login; **or**
- Set `user_id` to the user's production (live) Clerk user_id directly.

## Secrets check (requested)
- `ADMIN_EMAIL` — present, non-empty, equals `garciafinancas0073040@proton.me` (matches_expected=true).
- `CLERK_SECRET_KEY` — present, non-empty.
- `CLERK_PUBLISHABLE_KEY` — present, non-empty; is **pk_live** (differs from committed pk_test; `/api/__clerk` live-proxy active). No secret change needed — pk_live is correct for production.

## Not the cause
- Not a bad/empty secret (all required Clerk secrets present; ADMIN_EMAIL correct).
- Not token invalid (no 401) and not the intended 403 path.
- Not infra/tier/platform.
